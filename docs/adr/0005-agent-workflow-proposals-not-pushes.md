# ADR 0005: CI-run agents propose workflow changes; local sessions commit them directly

The agent-triage **CI run** (the `anomalyco/opencode/github` step in agent-triage.yml) may be asked to change files under `.github/workflows/`. Inside that run, the agent must never commit or push them: the run token has `contents: write` but lacks `workflows` permission, so GitHub rejects any push creating or updating workflow files. Instead, the agent runs `scripts/suggest-workflow-change.sh`, which writes the unified diff to a **Workflow Proposal** at `docs/workflow-proposals/<issue>-<timestamp>.md`, reverts the workflow files, and commits the proposal. A CI-only pre-commit hook (`.githooks-ci/pre-commit`, enabled via `core.hooksPath` set in agent-triage.yml) hard-blocks any commit staging `.github/workflows/*` so a missed instruction can never regress to a push failure. The PR body flags the proposal under "Workflow changes — proposed, not applied"; a proposal-only issue is not marked `Closes`.

**Scope:** this restriction binds only that CI run and its run token. Local/interactive sessions — or any push made with a credential that does hold `workflows` permission (PAT, SSH) — commit `.github/workflows/*` changes directly; the pre-commit hook is not installed there. Tell: `git config core.hooksPath` prints `.githooks-ci` in the CI run, nothing locally.

The alternative was granting `workflows: write` to the token (tried in `16c3984`, reverted in `4e2b3bc`). That would let a push succeed and gate the change behind human PR review — but it lets the agent change CI behaviour without a human-first diff, and it is a standing privilege that need not exist. Granting it would also have masked the fact that the agent cannot safely own workflow semantics yet. Proposing diffs keeps the token surface minimal and makes every workflow change an explicit, reviewable artifact. Scope is `.github/workflows/**` only; other `.github/` files (e.g. templates) are writable with `contents: write` and cause no push failure.
