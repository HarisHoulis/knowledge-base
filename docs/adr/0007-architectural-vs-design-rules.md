# ADR 0007: Architectural vs design rules

The committed agent rules in `docs/agents/` are split by reversibility and scope: `architectural-rules.md` records constraints (hard to reverse, system-wide), `design-rules.md` records guidelines (cheap to adjust, within a module), and `python-rules.md` records language idioms. All three are lazy-loaded from `AGENTS.md` via the opencode manual-instructions pattern (`@` references under an External File Loading block), so they are read on a need-to-know basis rather than always present in context. The content is grounded in *Fundamentals of Software Architecture* (Richards & Ford) — notably the laws of software architecture, connascence (Ch. 3), fitness functions (Ch. 6), reusable/autonomous components (Ch. 8), and right-sized decisions (Ch. 19). Separating constraints from guidelines keeps the hard, system-wide decisions prominent while leaving cheaper, local guidance free to evolve without reopening an ADR.

Enforcement is two-tier: mechanical rules are gated by CI via `scripts/check-rules.sh` (bare-`python` usage, AGENTS.md `@reference` resolution) and `scripts/check-fitness.py` (the `kb_pipeline/` dependency matrix and `pipeline.py` size baseline) alongside the existing mypy/ruff/pytest gates, while non-mechanical rules are enforced at review time via the auto-code-review Standards axis. The rule-to-mechanism map lives in `docs/agents/compliance.md`; because unenforced decisions decay silently, every rule in the three files carries a mechanism there.
