# API Auth for the Single-User Ktor REST API: Static Key vs Bearer vs JWT

Question: the backend is a self-hosted Ktor server (Kotlin) on a Hetzner VPS serving a REST/JSON API under `/api/v1` over the public internet to a Compose Multiplatform app (Android + iOS). There is exactly one human user, and the only credential can be shipped in the app binary (extractable). Content ingestion writes Postgres directly through the pipeline, never through this API — the API is read-mostly. What should protect the endpoints: a static API key in `X-API-Key`, a static bearer token in `Authorization: Bearer`, or a signed-in JWT/opaque-session token?

Findings below are grounded in primary sources: Ktor's official docs, RFC 6750/6749, OWASP MASVS/MASWE, and the Android/Apple platform security docs.

## Findings

### 1. Ktor ships first-party auth for all three options — guarding a route set is a documented one-step pattern

Ktor's `Authentication` plugin (`ktor-server-auth`) is the official mechanism, and the docs' canonical pattern for guarding a route group is to wrap the routes in `authenticate { ... }`, which only executes the nested handlers after a provider's `validate`/`authenticate` succeeds; on failure the provider's `challenge` responds `401`. All three candidate mechanisms are built in:

- **API key** — the `apiKey` provider (`ktor-server-auth-api-key`). By default reads the key from the `X-API-Key` header; `headerName` renames it. `validate { key -> ... }` returns a `Principal` or `null`; a null fails auth with `401 Unauthorized`. The docs' static-key example compares against a value read from `environment.config.property("api.key")` and state the secrets belong in config/env, not source.
- **Bearer** — the `bearer` provider. Reads `Authorization: Bearer <token>` and hands the token to `authenticate { tokenCredential -> ... }`; the docs explicitly say the provider supports "custom logic for authorizing bearer tokens" beyond OAuth/JWT — i.e., a statically held string is a supported use. Sets the `WWW-Authenticate: Bearer realm=...` challenge, per RFC 6750.
- **JWT** — the `jwt` provider (`ktor-server-auth-jwt`), with a signing-secret (`HS256`) or key-pair (`RS256`) verifier, claim validation, and the same `authenticate { ... }` route guard.

Both the API-key page ("API Keys should be kept secret and transmitted securely. It's recommended to use HTTPS/TLS to protect API keys in transit") and the bearer page ("Bearer authentication should only be used over HTTPS/TLS") make TLS a prerequisite; Ktor's SSL page covers serving HTTPS directly or behind a reverse proxy. So: all three options are equal citizens in Ktor, all route guards are the same `authenticate {}` call, and none is sanctioned to run without TLS.

Sources: [Ktor — Authentication and authorization](https://ktor.io/docs/server-auth.html) · [Ktor — API Key authentication](https://ktor.io/docs/server-api-key-auth.html) · [Ktor — Bearer authentication](https://ktor.io/docs/server-bearer-auth.html) · [Ktor — JWT](https://ktor.io/docs/server-jwt.html) · [Ktor — SSL and certificates](https://ktor.io/docs/server-ssl.html)

### 2. The static-secret vs short-lived-token tradeoff — what the standards actually say

**Bearer tokens, per RFC 6750, are "possession" credentials:** "Any party in possession of a bearer token (a 'bearer') can use it to get access to the associated resources." Its threat mitigation list therefore centers on *disclosure*: always use TLS, issue short-lived tokens ("one hour or less"), don't store them in cookies, don't put them in URLs, validate the cert chain. Those mitigations exist because in RFC 6750's world a token is a **short-lived access token minted by an authorization server**, and expiry is what limits blast radius if it leaks. A static API key or static bearer string is that same possession credential but with **no expiry** — compromise means permanent access until a human rotates it manually.

**The sign-in/JWT alternative does not escape the core problem here.** To bootstrap, a JWT flow still requires the app to hold something it can exchange for a token — a password, a client secret, or a signing secret. RFC 6749 is explicit that an app installed on a device cannot hold a confidential credential at all: native applications are defined as **public clients** — "incapable of maintaining the confidentiality of their credentials" — and §3.2.1 states "The authorization server MUST **NOT** issue client passwords or other client credentials to native application or user-agent-based application clients for the purpose of client authentication." Whatever static material a JWT flow needs to sign in is exactly as extractable as a static API key.

**OWASP's mobile standard names hardcoded secrets a first-class weakness.** MASWE-0004 ("Sensitive Data Hardcoded in the App Package") covers "API keys and secrets for first- or third-party services" and states plainly: "anyone who downloads the package can recover it." Its mitigations, in order: (1) proxy static secrets through a middleware/gateway so the secret never lives in the client, (2) **use stateful API services with "dynamic tokens that expire after a reasonably short time (e.g., 1 hour)"** and consider OAuth 2.0, (3) runtime secret retrieval behind a validated gateway, and — as a last resort — (4) keystore storage plus obfuscation/RASP, with the explicit caveat that "these techniques **deter but do not prevent extraction**."

So the honest tension, per the sources: a JWT/sign-in flow only adds value if it gives you **expiry and server-side revocation** — the ability to kill access after a compromise or a leak — and it still leaves an equally extractable bootstrap secret in the binary. For this system the API is read-mostly, the DB writes bypass it, and the only client is the owner's private app; the realistic adversary is a random internet scanner probing a public endpoint, not someone who has the APK. Against that adversary, a static secret over TLS and a JWT flow are **indistinguishable in effect**; against a determined adversary with the binary, both are equally defeated at the bootstrap step (RFC 6749 §3.2.1, MASWE-0004). A JWT flow buys revocation-of-expired-tokens and a server-side session kill switch, at the cost of a login endpoint, a sign-in credential to store, refresh-token handling, Keystore/Keychain plumbing, and re-login UX — all of it bespoke in a single-user system.

Sources: [RFC 6750 — Bearer Token Usage](https://www.rfc-editor.org/rfc/rfc6750.html) · [RFC 6749 — OAuth 2.0 (client types, §2.1; client authentication, §3.2.1)](https://www.rfc-editor.org/rfc/rfc6749.html) · [OWASP MASWE-0004 — Sensitive Data Hardcoded in the App Package](https://mas.owasp.org/MASWE/MASVS-STORAGE/MASWE-0004/)

### 3. On-device secret storage — Keystore/Keychain protect *at rest*, not *in the binary*

The platform primitives protect key material that is **generated or imported on the device**, and their own docs describe exactly that scope:

- **Android Keystore** makes keys "more difficult to extract from the device," keeps "key material never enter[ing] the application process," and can bind keys to the TEE/StrongBox hardware. But a key is only protected this way if it was generated/imported *into* the Keystore on that device — the Keystore provides no protection for a plaintext secret that ships inside the APK, which the app must contain to bootstrap. Android's own app-security guidance states the premise directly: "When your app is compiled, and your app's source code includes API keys, it's possible for an attacker to decompile the app and find these resources."
- **Android EncryptedSharedPreferences** (Jetpack Security) encrypts preference values at rest, with a master key held in the Android Keystore — i.e., protection of a secret *after first provisioning*, not of the provisioning path itself. It is precisely the "store the credential at rest" layer, not the "keep the credential secret" layer.
- **Apple Keychain** is "a mechanism to store small bits of user data in an encrypted database"; its documented contents are user-chosen secrets (passwords, keys, certificates) stored *on the user's behalf*. Like the Keystore, it protects an item that is written into it at runtime; it cannot retroactively protect a value that ships in the IPA.

The conclusion the sources force: Keystore/Keychain meaningfully raise the cost of on-device theft (other apps, backups, OS-level extraction) for a **provisioned** credential, but they are neutralized as a defense for a **bootstrap secret embedded in the binary** — anyone who can download the package can recover it (MASWE-0004), no keystore involved. So they are worth using for storing whatever credential the app holds, but they do not change the choice between static key and JWT.

Sources: [Android — Keystore system](https://developer.android.com/privacy-and-security/keystore) · [Android — App security best practices (API key management)](https://developer.android.com/topic/security/best-practices) · [Android — EncryptedSharedPreferences](https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences) · [Apple — Keychain services](https://developer.apple.com/documentation/security/keychain-services)

### 4. Rate limiting — warranted, and built into Ktor

Ktor ships a first-class `RateLimit` plugin (`ktor-server-rate-limit`): a token-bucket limiter, applied globally or per-route, keyed by `requestKey` (the docs' example is exactly "an IP address, an API key or access token"), returning `429 Too Many Requests` with `Retry-After`. The Ktor API-key best-practices list itself calls for combining API-key auth with rate limiting. OWASP's guidance on protecting against automated attacks (login throttling, monitoring) similarly frames limiting as defense-in-depth for anything reachable over the internet. For a single authenticated user, a per-key or per-IP limit on `/api/v1` is a few lines, costs nothing, and blocks the one real threat this API has — unauthenticated scanning/hammering of a public endpoint. Brief verdict: yes, warranted, trivially cheap.

Sources: [Ktor — Rate limiting](https://ktor.io/docs/server-rate-limit.html) · [Ktor — API Key authentication (best practices)](https://ktor.io/docs/server-api-key-auth.html) · [OWASP — Authentication Cheat Sheet (Protect Against Automated Attacks)](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

## Verdict

For this threat model — one private client, one user, read-mostly API, writes bypass the API — the sources support **a static shared secret over TLS, with rate limiting**; the JWT/sign-in flow is not justified by the standards.

- A static API key or static bearer string and a JWT flow are **cryptographically and practically equivalent at the bootstrap step**: the app must ship something extractable (RFC 6749 §3.2.1 defines native apps as public clients; MASWE-0004 says anything in the package is recoverable). Neither survives a determined attacker who holds the binary.
- The only thing a sign-in/JWT flow *does* buy — per RFC 6750's short-lived-token guidance and MASWE-0004's "dynamic tokens that expire" mitigation — is **expiry and revocation**: access dies after an hour and a server-side session can be killed. For a single-user personal API the realistic adversary (internet scanners, no binary access) makes that capability near-zero-value, while the cost is a bespoke login flow, sign-in credential storage, refresh handling, and re-login UX across Android + iOS.
- Between the two static options, Ktor's docs treat them as equivalent transports for a secret: `apiKey` defaults to `X-API-Key`; `bearer` reads `Authorization: Bearer` per RFC 6750. **Prefer `X-API-Key`** via the `apiKey` provider — it is the mechanism the Ktor docs document for "a simple authentication method where clients pass a secret key in a header," its page carries the operational best practices (env-var storage, rotation, rate limiting, cryptographically random key format), and it avoids implying the token came from an OAuth authorization server.

Recommended shape, all of it first-party Ktor: `apiKey` provider with `validate` reading the key from an environment variable (never source), `authenticate {}` wrapping the whole `/api/v1` route subtree, TLS/HTTPS in front of the Ktor server, and a `RateLimit` (per-IP or per-key, 429 on excess) on those routes. Keystore/Keychain should still hold the key on-device once provisioned — it protects at rest — but that is a hygiene layer, not the security decision.
