# Nightly device tests on GitHub-hosted macOS runners: Android emulator + iOS simulator for a Compose Multiplatform app

Question: can a nightly GitHub Actions workflow on `macos-latest` run both Android-emulator instrumented tests and iOS-simulator Compose UI tests (`runComposeUiTest` / `iosSimulatorArm64Test`) for the CMP app under `app/`, so heavy device tests stop slowing PRs? The repo is public, so minutes are free. The premise needs splitting in two, because the Android half has a hard host problem and the iOS half does not.

## Investigation Date

2026-08-23

## Findings

### 1. Android emulator on `macos-latest`: runnable in principle, but unaccelerated and effectively unusable as a CI gate today

**Hardware acceleration is only guaranteed on Linux runners.** GitHub's own runner docs state: "GitHub-hosted Linux runners support hardware acceleration for Android SDK tools, which makes running Android tests much faster and consumes fewer minutes." The macOS runner is not listed — acceleration there is not provided.

**`macos-latest` is now an arm64 M1 VM, and nested virtualization is explicitly unsupported.** The current `macos-latest` is `macos-26-arm64`: 3-core M1, 7 GB RAM, 14 GB SSD. GitHub's runner reference lists, under "Limitations for arm64 macOS runners": "Nested-virtualization is not supported due to the limitation of Apple's Virtualization Framework." The Android emulator gets its macOS acceleration from Apple's **Hypervisor.framework** (HVF); inside GitHub's M1 VMs HVF cannot initialize, so the emulator refuses to start. This is documented with a live repro in ReactiveCircus/android-emulator-runner:

- Issue #350 (open): launching an `arm64-v8a` AVD on an M1 `macos-latest` runner fails with `HVF error: HV_UNSUPPORTED` / `qemu-system-aarch64-headless: failed to initialize HVF: Invalid argument`.
- Issue #453 (closed Nov 2025): "macOS runner: emulator fails with HVF errors" for `arm64-v8a` images — still the state of the world.

**Which image arch to pick on macos-latest: there is no good pick.** The modern images Google ships for recent API levels are x86/x86_64 ("The old ARM-based emulators were slow and are no longer supported by Google"), and the `arm64-v8a` images that do exist are "limited to fewer API levels." On the arm64 host, `arm64-v8a` images need HVF (fails outright per above), and `x86_64` images run in pure software emulation with no HVF — boot times of 10+ minutes, frequently hitting the runner action's default `emulator-boot-timeout` of 600 seconds. So on current `macos-latest`, neither arch is viable for a nightly gate.

**What's preinstalled / recommended action.** The macOS runner image ships the Android SDK (Command Line Tools 16, Emulator 36.6.11, Build-tools 35–37, Platforms up to android-37.x, NDK 27/28/29, `ANDROID_HOME` set) — but **no system images**, so the AVD's system image must be downloaded at runtime. The de-facto standard action is `ReactiveCircus/android-emulator-runner` (used by coil, sqldelight, retrofit, compose-samples…); it installs the needed SDK components, creates the AVD, boots headless, waits for boot, and runs your Gradle script. Its README, however, is explicit about the host tradeoff: "It is now recommended to use the **Ubuntu** (`ubuntu-latest`) runners which are 2-3 times faster than the **macOS** ones." Historical data point from the action's author (Intel-macOS era, HAXM-accelerated, 10 modules / 160 instrumented tests): ~20 min for the whole workflow. Unaccelerated-on-arm64 is strictly worse.

**Bottom line for #1:** an Android emulator on `macos-latest` does not get hardware acceleration, and on the current arm64 image the emulator either fails to start (arm64-v8a, HVF) or boots in software emulation that is too slow to be a reliable nightly. Android instrumented tests belong on `ubuntu-latest` (free on this public repo, KVM-accelerated, 4-core/16 GB, same preinstalled Android SDK).

### 2. iOS simulator on `macos-latest`: feasible and low-friction

**The task exists and is the documented way to run Compose UI tests on iOS.** The CMP UI-testing guide's canonical command is `./gradlew :shared:iosSimulatorArm64Test`, running the same `runComposeUiTest` API used for common/desktop tests. `iosSimulatorArm64` is a Tier-1 Kotlin/Native target whose tests "can be run on the host" — specifically the macOS ARM64 host, which is exactly what `macos-latest` is.

**The runner already has everything needed.** The `macos-26-arm64` image ships Xcode 26.6 (default) with iOS 26.x SDKs and **preinstalled iOS simulators** (iPhone 17 family, iPads, runtimes 26.2/26.4/26.5). No Xcode setup step is needed beyond what the image provides, and no Apple developer account/signing: provisioning profiles are only required for physical-device runs, not simulator destinations.

**How the simulator runs in headless CI.** The Kotlin/Native test executor (JetBrains source) invokes `xcrun simctl`: it lists runtimes/devices, creates the target device (`simctl create`, default `iPhone-14` device type when unspecified) if it does not exist, and launches the test binary with `simctl spawn --standalone <device> <test-executable>` (env passed as `SIMCTL_CHILD_*`). Because the iOS runtime is preinstalled on the image, the expensive fallback — `xcodebuild -downloadPlatform` — is skipped. The simulator does not need a window; `simctl` operates headless. Practical hardening for CI is to pre-boot a device (`xcrun simctl boot`) before the test task to avoid first-boot jitter, but the task itself is self-sufficient.

**Cold-start cost.** The dominant cost is the first Kotlin/Native compile of the shared module + test binary on a 3-core M1, plus the one-time `~/.konan` download (~1 GB toolchain) and Gradle dependency resolution. This matches the prior research on this repo (docs/research/agent-machine-options.md, from #165) that flagged first K/N iOS builds as slow and called for Gradle + `~/.konan` caching. Kotlin's own docs say the first Gradle compile is slower than later ones and that `~/.konan` should be preserved between CI builds. Working estimate for a small CMP `shared` module: **cold (no caches) ≈ 10–20 min; warm (cached `~/.konan` + Gradle) ≈ 3–8 min for build, plus ~1–3 min simulator boot + test execution**. Treat the numbers as estimates to be measured on the first real run.

### 3. One job running both, vs two jobs: split them — and put Android on Linux

**One `macos-latest` job doing both is the wrong shape.** The arm64 macOS runner has 3 cores and 7 GB RAM. Running an (unaccelerated, borderline-broken) Android emulator *and* an iOS simulator *and* a Kotlin/Native compile in one job means severe resource contention and flakiness on top of Finding #1's emulator problem. There is also no real cost saving to forcing it into one job: standard runners are free on public repos either way.

**Recommended layout: two independent jobs, different hosts.**

- `android-nightly` on **`ubuntu-latest`** — KVM-accelerated emulator via `ReactiveCircus/android-emulator-runner` (enable KVM per the README), `./gradlew :shared:connectedAndroidTest` (the CMP-documented instrumented-test task). This is the configuration the action itself recommends and is 2–3× faster than macOS. The Ubuntu image preinstalls the Android SDK toolchain (build-tools, platforms, NDK); the action installs the emulator + system image at runtime.
- `ios-nightly` on **`macos-latest`** — `./gradlew :shared:iosSimulatorArm64Test` (Finding #2).

**Constraints on parallelism / scheduling:** on the GitHub Free plan, max 20 concurrent jobs with **max 5 concurrent macOS jobs**; macOS capacity is shared across standard + larger runners. Two nightly jobs is trivially within that. A `cron` trigger runs on the latest commit of the **default branch only**, and the workflow file must exist on the default branch to fire. Scheduled runs can be delayed or even dropped during high-load windows (notably the top of each hour), and on public repos a scheduled workflow **auto-disables after 60 days of no repository activity**. Overlapping runs (e.g., a nightly that overruns into the next) are allowed by default and run concurrently; use a top-level `concurrency:` group (`cancel-in-progress: true` or `queue: max`, up to 100 queued) to serialize/guarantee a single nightly at a time.

### 4. Scheduled workflows, manual runs, overlap, and free-tier accounting

- **`cron` runs on the default branch only** ("Scheduled workflows will only run on the default branch"), shortest interval 5 minutes, timezone-aware via an `IANA` `timezone:` field. Runs on the latest commit of the default branch.
- **`workflow_dispatch`** enables manual runs from the Actions tab/CLI/API, with optional typed inputs; the trigger only fires when the workflow file is on the default branch.
- **Overlap/queueing:** by default multiple runs execute concurrently up to account concurrency limits; there is no automatic queue. Use `concurrency:` groups to keep one nightly at a time (default `queue: single` cancels pending runs in the group; `queue: max` allows up to 100 pending).
- **Free-tier minutes:** "Use of the standard GitHub-hosted runners is free and unlimited on public repositories" — including macOS. Minutes only apply to private repos (2,000/month on GitHub Free); **larger runners are never free even on public repos**; per-repo cache storage is 10 GB free on all plans; artifact storage 500 MB on Free.

### 5. The "30-minute" concern: there is no 30-minute platform cap, and the job fits — with caching

**Clarify the constraint first.** GitHub's per-job timeout default is **360 minutes (6 hours)** (`timeout-minutes`); there is no 30-minute platform limit. The 30-minute timeout in this repo is a *self-imposed* `timeout-minutes: 30` on the opencode step in `.github/workflows/agent-triage.yml` (from the #165-era agent research) — a nightly workflow is free to set its own `timeout-minutes`, e.g. 45–60 min per job. The risk #165 flagged is real but only affects the *first* cold build.

**Estimated per-job budget (warm, with caching):**

- `ios-nightly` (macos-latest): checkout ~10s → Gradle config + K/N compile of `shared` + iOS test binary ~3–8 min → simulator boot ~1–2 min → `iosSimulatorArm64Test` ~1–3 min → **≈ 10–20 min total**. Cold (no caches): K/N toolchain download + full compile can push the build step past 30 min.
- `android-nightly` (ubuntu-latest): checkout → `assembleDebug`/`assembleDebugAndroidTest` ~2–5 min → emulator/system-image install ~2–4 min → boot (KVM) ~1–4 min → `connectedAndroidTest` ~2–5 min → **≈ 10–20 min total**.

**Mitigations to keep the iOS build step comfortably inside 30 minutes:**

1. Cache `~/.konan` (the Kotlin/Native toolchain + caches, ~1 GB) via `actions/cache`, or relocate it with the `konan.data.dir` Gradle property — Kotlin's docs recommend preserving it across CI builds.
2. Cache Gradle via `gradle/actions/setup-gradle` (caches wrapper, dependencies, and build outputs; within the 10 GB free cache).
3. Enable `org.gradle.caching=true` (Gradle build cache) and the configuration cache (`org.gradle.configuration-cache=true`); bump heap with `org.gradle.jvmargs=-Xmx3g` (Kotlin doc recommendation).
4. Run only the tasks needed: `:shared:iosSimulatorArm64Test` and `:shared:connectedAndroidTest` — not `build`/`assemble` (which rebuild code multiple times and build release binaries; release K/N compilation takes "an order of magnitude" longer than debug). Avoid `*XCFramework` tasks, which compile all targets.
5. Split the build and the test into separate steps so each step's `timeout-minutes` covers only its phase, and set a job-level `timeout-minutes` above the default so slow first runs fail loudly rather than being killed mid-test.
6. Optionally pre-boot the simulator (`xcrun simctl boot`) and, on Android, use AVD snapshot caching (the emulator-runner README documents the two-step snapshot pattern) to cut boot time further.

Sources: [GitHub — Workflow syntax, `timeout-minutes` (default 360)](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions) · [GitHub — Actions limits (6h job execution)](https://docs.github.com/en/actions/reference/limits) · [Kotlin — Tips for improving compilation time (`~/.konan`, build cache, `-Xmx3g`, avoid release/whole-project builds)](https://kotlinlang.org/docs/native-improving-compilation-time.html) · [ReactiveCircus/android-emulator-runner README (AVD snapshot caching pattern)](https://github.com/ReactiveCircus/android-emulator-runner) · [This repo — `.github/workflows/agent-triage.yml` (the existing 30-min step timeout)](https://github.com/HarisHoulis/knowledge-base/blob/main/.github/workflows/agent-triage.yml)

## Verdict

**Feasible — but not as one `macos-latest` job, and not with Android on macOS.**

- **iOS simulator tests on `macos-latest`: yes, cleanly.** `iosSimulatorArm64Test` + `runComposeUiTest` run headless on the preinstalled Xcode/iOS simulator toolchain with no signing and no extra setup; the K/N executor drives everything via `simctl`. Cold-first-build cost is the only real risk and is mitigated by caching `~/.konan` + Gradle and by setting a sane job timeout.
- **Android emulator on `macos-latest`: no.** It gets no hardware acceleration (GitHub only provides it on Linux runners), and on the current arm64 image the emulator either dies on HVF init (`HV_UNSUPPORTED`) for `arm64-v8a` images or runs too slowly unaccelerated for `x86_64`. This is the part of the premise to drop.
- **Recommended layout — two jobs in one scheduled workflow:**
  - `android-nightly` → `ubuntu-latest` + `ReactiveCircus/android-emulator-runner` (enable KVM) → `:shared:connectedAndroidTest`.
  - `ios-nightly` → `macos-latest` → `:shared:iosSimulatorArm64Test`, with `~/.konan` + Gradle caching and `timeout-minutes` set to 45–60 at job level.
  - Trigger: `schedule` cron (default-branch only) + `workflow_dispatch` for manual kicks; add a `concurrency:` group (`cancel-in-progress: true`) so an overrun never stacks nightlies. Free on this public repo (standard runners incl. macOS are unlimited; larger runners are never free).

**Gotchas to carry forward:** scheduled workflows only run on the default branch and auto-disable after 60 days without repo activity on public repos; scheduled runs may be delayed/dropped at high-load hours (avoid `:00` if it matters); macOS concurrency is capped at 5 concurrent jobs on the Free plan; the image ships no Android system images (downloaded at runtime) and no arm64 iOS simulator boot is needed since the runtime is preinstalled; no platform 30-min limit exists — that figure is only the agent-triage step's own timeout.
