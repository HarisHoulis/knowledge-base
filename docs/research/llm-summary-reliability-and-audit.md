# LLM Summary Reliability and the Generate-Then-Audit Loop

## Investigation

This document answers the research questions behind issue-level failures in the knowledge-base pipeline: a `classify_summarize` call that emits empty or truncated JSON, and audit verdicts that truncate. The relevant request shapes today are:

- Classify (`kb_pipeline/llm.py`): no `thinking` field; `response_format: {"type": "json_object"}`; `temperature: 0.3`; `max_tokens: 2000`.
- Audit (`kb_pipeline/audit.py`): `"thinking": {"type": "disabled"}`; `response_format: {"type": "json_object"}`; `temperature: 0.1`; `max_tokens: 1000`.
- Model/endpoint: `deepseek-flash` via `https://api.deepseek.com/v1`.

Run logs show `finish_reason='length'`, `completion_tokens` pinned at the cap, and `reasoning_tokens` consuming 1492–2000 of the 2000 budget on classify. The questions below span API mechanics (Q1–Q2), the research evidence on chain-of-thought faithfulness (Q3), self-verification limits (Q4), anti-hallucination techniques (Q5), and same-family judge bias (Q6).

Method note: every substantive claim in "What the sources say" is anchored to a primary source (vendor doc or the paper itself) with a short verbatim quote. Where a question could not be anchored, that is stated explicitly. The legacy `deepseek-reasoner` doc is surfaced where it conflicts with the current unified docs, because that conflict is load-bearing for the pipeline's diagnosis.

## What the sources say

## 1. DeepSeek API mechanics (Q1)

**Thinking mode is on by default at effort `high`.** The Thinking Mode guide states the toggle and default:

- `{"thinking": {"type": "enabled/disabled"}}`
- Quote: "Thinking mode is enabled by default, with the default effort being `high`"
- Source: https://api-docs.deepseek.com/guides/thinking_mode

The API reference corroborates the default at the field level:

- `thinking` object: "**Default value:** `enabled`" and "If set to `enabled`, then use thinking mode. If set to `disabled`, then use non-thinking model."
- Source: https://api-docs.deepseek.com/api/create-chat-completion

**The documented way to disable thinking is `{"thinking": {"type": "disabled"}}`.** The guide lists that exact control parameter; the API reference repeats it as `Possible values: [enabled, disabled]`. (Same two URLs.) The audit call already uses this form.

**`temperature` is ignored while thinking is on; `top_p` has inverted, mode-dependent behavior.** The Thinking Mode guide:

- Quote: "Thinking mode does not support the `temperature`, `presence_penalty`, or `frequency_penalty` parameters. Please note that, for compatibility with existing software, setting these parameters will not trigger an error but will also have no effect."
- Quote: "`top_p` only takes effect in thinking mode, where the effective range is `0.95`–`1.0`: values below `0.95` are treated as `0.95`. In non-thinking mode it is fixed at `1.0` and your value is ignored."
- Source: https://api-docs.deepseek.com/guides/thinking_mode

The API reference matches: `temperature` "Has no effect in thinking mode."; `top_p` "only takes effect in thinking mode, where the effective range is 0.95–1.0 ... In non-thinking mode it is fixed at 1.0 and the value you pass is ignored." (https://api-docs.deepseek.com/api/create-chat-completion). Consequence for the pipeline: the classify call's `temperature: 0.3` is a no-op while thinking stays enabled, and the audit's `temperature: 0.1` only has effect because audit thinking is disabled.

**The chain-of-thought is returned separately as `reasoning_content`, and reasoning token counts appear under `completion_tokens_details`.**

- Quote: "In thinking mode, the chain-of-thought content is returned via the `reasoning_content` parameter, at the same level as `content`."
- Source: https://api-docs.deepseek.com/guides/thinking_mode
- `usage.completion_tokens` = "Number of tokens in the generated completion."; `usage.completion_tokens_details` = "Breakdown of tokens used in a completion."; `usage.completion_tokens_details.reasoning_tokens` = "Tokens generated by the model for reasoning."
- Source: https://api-docs.deepseek.com/api/create-chat-completion

**`finish_reason: "length"` means the token cap was hit, and the content may be cut mid-message.**

- `finish_reason` possible values include: "`length` if the maximum number of tokens specified in the request was reached".
- On `response_format`: "Also note that the message content may be partially cut off if finish_reason=\"length\", which indicates the generation exceeded max_tokens or the conversation exceeded the max context length."
- Source: https://api-docs.deepseek.com/api/create-chat-completion

The full enum is `[stop, length, content_filter, tool_calls, insufficient_system_resource, aborted]` — so truncation can also arise from `content_filter` or `insufficient_system_resource`, not only `length` (same URL).

**Does `reasoning_tokens` consume `max_tokens`? The current docs do not say so explicitly, and a legacy DeepSeek page says the opposite.**

- Current `max_tokens` definition: "The maximum number of tokens that can be generated in the chat completion." and "When not set, the default is 8K in non-thinking mode, 64K in thinking mode (128K with `reasoning_effort` set to `max`)."
- Source: https://api-docs.deepseek.com/api/create-chat-completion

The current definition says "generated in the chat completion" and nests `reasoning_tokens` inside `completion_tokens_details`, which is consistent with reasoning counting toward the cap — but it never states the inclusion directly. By contrast, the archived DeepSeek page for the legacy `deepseek-reasoner` model states the exclusion explicitly:

- Quote: "`max_tokens`：The maximum length of the final response after the CoT output is completed, defaulting to 4K, with a maximum of 8K. Note that the CoT output can reach up to 32K tokens".
- Source (archived, 2025-01-20): https://web.archive.org/web/20250120114627/https://api-docs.deepseek.com/guides/reasoning_model

**Uncertainty flag:** the current `deepseek-flash` (DeepSeek-V4.1-Flash) docs do **not** contain a sentence stating whether `reasoning_tokens` count against `max_tokens`. The only explicit statement found is the legacy one above, which says CoT is *excluded* — the opposite of the pipeline's stated root cause. The pipeline's empirical signal (`completion_tokens` pinned at 2000 with `reasoning_tokens` near 2000) is what actually establishes the budget is shared for this endpoint/model; the current docs alone do not. Pricing confirms `deepseek-flash` = DeepSeek-V4.1-Flash (https://api-docs.deepseek.com/quick_start/pricing).

## 2. JSON output reliability on DeepSeek (Q2)

The official JSON Output guide gives a four-point recipe, including an explicit acknowledgment of occasional empty content and a directive to size `max_tokens`:

- Quote: "To enable JSON Output, users should:"
  1. "Set the `response_format` parameter to `{'type': 'json_object'}`."
  2. "Include the word \"json\" in the system or user prompt, and provide an example of the desired JSON format to guide the model in outputting valid JSON."
  3. "Set the `max_tokens` parameter reasonably to prevent the JSON string from being truncated midway."
  4. "When using the JSON Output feature, the API may occasionally return empty content. We are actively working on optimizing this issue. You can try modifying the prompt to mitigate such problems."
- Source: https://api-docs.deepseek.com/guides/json_mode

Only `text` and `json_object` are valid `response_format` values, so schema-enforced decoding is not an available knob on this endpoint:

- Quote: "Must be one of `text` or `json_object`."
- Source: https://api-docs.deepseek.com/api/create-chat-completion

The API reference warns that omitting a JSON instruction in the prompt can produce runaway whitespace, and repeats the truncation caveat:

- Quote: "**Important:** When using JSON Output, you must also instruct the model to produce JSON yourself via a system or user message. Without this, the model may generate an unending stream of whitespace until the generation reaches the token limit, resulting in a long-running and seemingly \"stuck\" request."
- Source: https://api-docs.deepseek.com/api/create-chat-completion

Observed pipeline gap: the current `SYSTEM_PROMPT` recipe names fields but (per the prior repo research) supplies no example object; the guide requires an example and the word "json".

## 3. Does chain-of-thought improve or degrade faithfulness/hallucination for grounded work? (Q3)

**Evidence that CoT improves task performance (mostly reasoning, not grounded summarization):**

- Wei et al., *Chain-of-Thought Prompting Elicits Reasoning in Large Language Models*: "chain of thought prompting improves performance on a range of arithmetic, commonsense, and symbolic reasoning tasks." (https://arxiv.org/abs/2201.11903)
- Wang et al., *Self-Consistency Improves Chain of Thought Reasoning*: "self-consistency boosts the performance of chain-of-thought prompting with a striking margin on a range of popular arithmetic and commonsense reasoning benchmarks". (https://arxiv.org/abs/2203.11171)
- Wang et al., *Towards Understanding CoT: What Matters*: "CoT reasoning is possible even with invalid demonstrations - prompting with invalid reasoning steps can achieve over 80-90% of the performance obtained using CoT ... while still generating coherent lines of reasoning during inference." This shows the stated chain can be decoupled from what drives the answer. (https://arxiv.org/abs/2212.10001)

**Evidence that stated CoT is often unfaithful and can degrade accuracy:**

- Turpin et al., *Language Models Don't Always Say What They Think*: "we find that CoT explanations can systematically misrepresent the true reason for a model's prediction." and "This causes accuracy to drop by as much as 36% on a suite of 13 tasks from BIG-Bench Hard". (https://arxiv.org/abs/2305.04388)
- Lanham et al., *Measuring Faithfulness in CoT Reasoning*: "As models become larger and more capable, they produce less faithful reasoning on most tasks we study." and "Overall, our results suggest that CoT can be faithful if the circumstances such as the model size and task are carefully chosen." (https://arxiv.org/abs/2307.13702)
- Ye & Durrett, *The Unreliability of Explanations in Few-shot Prompting*: "explanations generated by the LLMs may not entail the models' predictions nor be factually grounded in the input, even on simple tasks with extractive explanations." (https://arxiv.org/abs/2205.03401)

**Evidence that structured/decomposition CoT can improve faithfulness:**

- Lyu et al., *Faithful Chain-of-Thought Reasoning*: "This guarantees that the reasoning chain provides a faithful explanation of the final answer." (https://arxiv.org/abs/2301.13379)
- Radhakrishnan et al., *Question Decomposition Improves the Faithfulness of Model-Generated Reasoning*: "By forcing the model to answer simpler subquestions in separate contexts, we greatly increase the faithfulness of model-generated reasoning over CoT, while still achieving some of the performance gains of CoT." (https://arxiv.org/abs/2307.11768)

**Uncertainty flag:** the primary literature above is dominated by reasoning/QA benchmarks. I could not find a primary paper that directly measures whether enabling an internal reasoning/thinking mode *improves or degrades* faithfulness of a grounded abstractive summary against its source (the pipeline's exact task). The closest grounded-task evidence is indirect (Cot faithfulness studies and CoVe, below). This is a genuine gap, not an assertion.

## 4. LLM self-verification: can an LLM reliably audit its own output? (Q4)

**Self-correction without external signal is unreliable, and can hurt:**

- Huang et al., *Large Language Models Cannot Self-Correct Reasoning Yet*: "our research indicates that LLMs struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction." (https://arxiv.org/abs/2310.01798)
- Tyen et al., *LLMs cannot find reasoning errors, but can correct them given the error location*: "poor self-correction performance stems from LLMs' inability to find logical mistakes, rather than their ability to correct a known mistake." (https://arxiv.org/abs/2311.08516)
- Stechly et al., *On the Self-Verification Limitations of LLMs on Reasoning and Planning Tasks*: "We observe significant performance collapse with self-critique and significant performance gains with sound external verification." (https://arxiv.org/abs/2402.08115)
- Valmeekam et al., *Can LLMs Really Improve by Self-critiquing Their Own Plans?*: "self-critiquing appears to diminish plan generation performance ... the LLM verifiers in that system produce a notable number of false positives, compromising the system's reliability." (https://arxiv.org/abs/2310.08118)

**Countervailing evidence that self-feedback can help on some tasks:**

- Madaan et al., *Self-Refine*: "Across all evaluated tasks, outputs generated with Self-Refine are preferred by humans and automatic metrics over those generated with the same LLM using conventional one-step generation, improving by ~20% absolute on average in task performance." (https://arxiv.org/abs/2303.17651)

**External feedback / tools are the reliable lever:**

- Gou et al., *CRITIC*: "our research highlights the crucial importance of external feedback in promoting the ongoing self-improvement of LLMs." (https://arxiv.org/abs/2305.11738)
- Kadavath et al., *Language Models (Mostly) Know What They Know*: models can self-evaluate with "encouraging performance, calibration, and scaling for P(True) on a diverse array of tasks", though "they struggle with calibration of P(IK) on new tasks." (https://arxiv.org/abs/2207.05221)

**Independent verifier / different model as judge:**

- Verga et al., *Replacing Judges with Juries* (PoLL): "using a PoLL composed of a larger number of smaller models outperforms a single large judge, exhibits less intra-model bias due to its composition of disjoint model families, and does so while being over seven times less expensive." (https://arxiv.org/abs/2404.18796)

## 5. Effective, source-anchored anti-hallucination techniques and their limits (Q5)

**Entailment/NLI fact-checking against source:**

- Maynez et al., *On Faithfulness and Factuality in Abstractive Summarization*: "we show that textual entailment measures better correlate with faithfulness than standard metrics". (https://arxiv.org/abs/2005.00661)
- Laban et al., *SummaC*: "SummaCConv obtains state-of-the-art results with a balanced accuracy of 74.4%, a 5% point improvement compared to prior work." (https://arxiv.org/abs/2111.09525)
- Honovich et al., *TRUE*: "we find that large-scale NLI and question generation-and-answering-based approaches achieve strong and complementary results." (https://arxiv.org/abs/2204.04991)
- Tang et al., *MiniCheck*: "Our best system MiniCheck-FT5 (770M parameters) outperforms all systems of comparable size and reaches GPT-4 accuracy" at "400x lower cost". (https://arxiv.org/abs/2404.10774)

**Citation grounding:**

- Gao et al., *ALCE*: "on the ELI5 dataset, even the best models lack complete citation support 50% of the time." (https://arxiv.org/abs/2305.14627)

**Constrained/structured decoding — guarantees format, can cost reasoning quality:**

- Willard & Louf, *Efficient Guided Generation*: the approach "enables the construction of reliable interfaces by guaranteeing the structure of the generated text." (https://arxiv.org/abs/2307.09702)
- Tam et al., *Let Me Speak Freely?*: "we observe a significant decline in LLMs reasoning abilities under format restrictions. Furthermore, we find that stricter format constraints generally lead to greater performance degradation in reasoning tasks." (https://arxiv.org/abs/2408.02442)

**Verification passes (decomposed self-check) and self-consistency:**

- Dhuliawala et al., *Chain-of-Verification*: "we show CoVe decreases hallucinations across a variety of tasks, from list-based questions from Wikidata, closed book MultiSpanQA and longform text generation." (https://arxiv.org/abs/2309.11495)
- Manakul et al., *SelfCheckGPT*: "for hallucinated facts, stochastically sampled responses are likely to diverge and contradict one another." Detects hallucination in a black-box, zero-resource setting. (https://arxiv.org/abs/2303.08896)
- Asai et al., *Self-RAG*: reflection tokens let a model "tailor its behavior"; it "shows significant gains in improving factuality and citation accuracy for long-form generations". (https://arxiv.org/abs/2310.11511)
- Wei et al., *Long-form factuality (SAFE)*: "SAFE agrees with crowdsourced human annotators 72% of the time, and ... SAFE wins 76% of the time" on a disagreement subset, at "more than 20 times cheaper than human annotators." (https://arxiv.org/abs/2403.18802)

**Fundamental limit:**

- Xu et al., *Hallucination is Inevitable*: "we formalize the problem and show that it is impossible to eliminate hallucination in LLMs." (https://arxiv.org/abs/2401.11817)

**Low temperature:** The only primary anchor found here is DeepSeek's own doc that `temperature` has no effect in thinking mode and that `top_p` is pinned to 1.0 in non-thinking mode (Q1). I could **not** find a primary paper establishing that lowering temperature reduces hallucination in grounded summarization; treat "low temperature reduces hallucination" as unanchored. (The DeepSeek high/off-peak price halves at off-peak hours, so cost is not the constraint either: https://api-docs.deepseek.com/quick_start/pricing.)

## 6. Same-family verifier: correlated blind spots / self-preference bias (Q6)

**Self-preference bias is documented:**

- Panickssery et al., *LLM Evaluators Recognize and Favor Their Own Generations*: "we discover a linear correlation between self-recognition capability and the strength of self-preference bias; using controlled experiments, we show that the causal explanation resists straightforward confounders." (https://arxiv.org/abs/2404.13076)
- Wataoka et al., *Self-Preference Bias in LLM-as-a-Judge*: "Our experimental results demonstrate that GPT-4 exhibits a significant degree of self-preference bias." and "the essence of the bias lies in perplexity and that the self-preference bias exists because LLMs prefer texts more familiar to them." (https://arxiv.org/abs/2410.21819)

**Judges carry other systematic biases even when not self-preferring:**

- Zheng et al., *Judging LLM-as-a-Judge*: "We examine the usage and limitations of LLM-as-a-judge, including position, verbosity, and self-enhancement biases, as well as limited reasoning ability". (https://arxiv.org/abs/2306.05685)
- Wang et al., *Large Language Models are not Fair Evaluators*: "the quality ranking of candidate responses can be easily hacked by simply altering their order of appearance in the context. This manipulation allows us to skew the evaluation result, making one model appear considerably superior to the other, e.g., Vicuna-13B could beat ChatGPT on 66 over 80 tested queries with ChatGPT as an evaluator." (https://arxiv.org/abs/2305.17926)

**Mitigation: disjoint model families reduce intra-model bias:**

- PoLL: "exhibits less intra-model bias due to its composition of disjoint model families". (https://arxiv.org/abs/2404.18796)

**Conflicting primary source (self-preference not universally observed):**

- Ho et al., *Reassessing Extractive QA Datasets at Scale*: "Contrary to findings in other NLP tasks, we observe no self-preference bias, even when the same model serves as both QA model and judge." (https://arxiv.org/abs/2504.11972)

## What I'd do next

**This section is the agent's recommendation — judgment, not fact. It is input to your decision.**

1. **Treat the audit LLM as a weak gate, not a truth oracle.** The evidence (Q4, Q6) is that a same-model, same-family verifier has correlated blind spots and measurable self-preference, and that self-critique can reduce performance absent external signal. A single `deepseek-flash` content audit is structurally the weakest form of this pattern. Highest-leverage change: add a **different-family verifier** (PoLL-style) or an **NLI/entailment fact-checker** against the source (MiniCheck/SummaC/TRUE), which are primary-source-backed and cheap. This does not require abandoning the existing audit; it makes it a second opinion rather than the only one.

2. **Fix the classify request to match the audit's budget discipline** (this part is anchored in Q1/Q2): disable thinking for structured extraction, raise `max_tokens` for real headroom, complete the JSON recipe with the word "json" plus a one-shot example, and log `finish_reason` + `usage` (including `reasoning_tokens`) on every failure so the empty-vs-truncated distinction becomes attributable. Add one retry on empty/`length` bodies. This mirrors the existing repo plan; the research adds no reason to reverse it.

3. **Do not over-invest in enabling thinking for the summary step on the assumption it improves faithfulness.** The primary evidence (Q3) is that stated CoT is frequently unfaithful and that enabling it costs budget; the direct evidence that thinking improves *grounded summarization* faithfulness is missing (flagged gap). If you want reasoning for summaries, use structured verification (CoVe) rather than free-form thinking.

4. **Keep audits fail-closed and independent of the verdict parse.** A malformed audit body must not auto-pass content (the prior repo finding). With a same-family judge, fail-open is the single most dangerous behavior in the loop.

5. **Prefer source entailing checks over style/citation-only checks.** ALCE's result (best systems lack complete citation support 50% of the time) argues citations alone are not a sufficient gate; pair citations with entailment.

## Confidence and strongest counterargument

**Confidence: moderate.** The API-mechanics facts (Q1, Q2) are high-confidence: they are quoted from current official DeepSeek docs. The research conclusions (Q3–Q6) are moderate: they are anchored to peer-reviewed/primary papers, but the evidence base is dominated by reasoning and QA rather than grounded summarization specifically, and one key question (does reasoning consume `max_tokens` on the current `deepseek-flash`) is not explicitly resolvable from the current docs alone (the legacy page conflicts).

**Strongest counterargument (a real, conflicting primary source, not a strawman):** Ho et al., *Reassessing Extractive QA Datasets at Scale* (arXiv:2504.11972) find "no self-preference bias, even when the same model serves as both QA model and judge", and report LLM-as-a-judge correlations with humans "up to 0.85". Taken seriously, this weakens the claim that a same-family verifier necessarily produces correlated blind spots in *extraction-style* tasks (the pipeline's classification/grounding check is closer to extractive QA than to open-ended judging). If the bias is task-dependent and absent for objective grounding checks, then paying for a second model family may buy little; the cheaper, higher-leverage move would instead be to make the existing check *objective and source-anchored* (entailment/citation verification) rather than to add a second LLM judge. This is a genuine open question the paper raises, and it is the strongest reason to pilot the independent-verifier change against a labelled fixture set before committing to it.

A second conflicting source on the self-correction side: Madaan et al., *Self-Refine* (arXiv:2303.17651) report "~20% absolute on average" gains from a single model acting as generator, refiner, and feedback provider — direct evidence that self-feedback can help on some tasks, against the Huang/Stechly pessimism. The reconciliation offered by Tyen et al. (arXiv:2311.08516) — models can correct a *located* mistake but struggle to *find* it — suggests the pipeline's structured, surgical audit feedback (which supplies the location) may fare better than the generic self-critique failure cases. This is a reason to keep the audit-retry loop while strengthening the verifier, not a reason to dismiss the pessimism.

**Questions I could not anchor:**
- Q1: whether `reasoning_tokens` count against `max_tokens` on the current unified `deepseek-flash` model (current docs silent; legacy doc says no; only empirical logs indicate yes).
- Q3: a primary study directly measuring thinking-mode effect on grounded summarization faithfulness (the exact pipeline task).
- Q5: a primary anchor that low `temperature` reduces hallucination in grounded summarization.

## Recommendation summary

Keep the existing request-parameter fixes (disable thinking + raise `max_tokens` + complete the JSON recipe + failure logging + fail-closed audits), because Q1/Q2 anchor them directly and the alternative explanation for the budget overrun is not documented for the current model. The larger architectural question — whether a same-model audit is trustworthy — is only partially settled: the bias literature (Q6) says same-family judges are suspect, but Ho et al. show the bias is task-dependent and can be absent for objective extraction. The recommended shape is therefore: make the audit **objectively source-anchored** (entailment/citation verification) and, if budget allows, add a **disjoint-model second opinion**, then validate both against the repo's hand-crafted correct/incorrect fixtures before trusting the gate. Decide with the counterargument above in view.
