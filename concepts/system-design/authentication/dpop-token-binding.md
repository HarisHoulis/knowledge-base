# Google Adopts DPoP to Strengthen OAuth 2.0 Against Token Theft and Replay Attacks

Google's OAuth Platform has added support for Demonstrating Proof-of-Possession (DPoP), an OAuth 2.0 mechanism that mitigates token theft and replay attacks. Traditional bearer tokens follow a "finders-keepers" model, leaving them exposed to Infostealer malware such as RedLine and NodeStealer and to Adversary-in-the-Middle attacks. DPoP uses cryptography to bind tokens to an asymmetric key pair generated by the client, so a stolen token cannot be replayed without the corresponding private key, which stays under the client's control.

Google applies DPoP only to refresh tokens, not access tokens. Long-lived refresh tokens are described as "the primary vector for persistent online impersonation," while applying DPoP to short-lived access tokens would add "asymmetric cryptographic verification overhead" to every request. Adopting DPoP imposes client-side work: generating cryptographic keys, handling timestamps and nonces, and producing the appropriate HTTP headers and DPoP proof JWTs.

DPoP does not protect standard web session cookies, which remain vulnerable to Infostealer malware. For that threat, Google and the WICG are developing Device Bound Session Credentials (DBSC), which cryptographically bind browser session cookies to device hardware such as a TPM. Together, DPoP and DBSC form a defense-in-depth strategy covering both API tokens and web sessions.

Google notes DPoP is unsuitable for multi-agent workflows, since delegating a task would require a second agent to sign on behalf of the first, which is impossible without accessing the first agent's private key. Instead, Google recommends Google Cloud Secure Token Service (STS), where an intermediate agent exchanges the upstream token for a new short-lived federated token bound to its own key pair, preserving sender-constrained security across the agent chain. Because the DPoP private key lives client-side, its security depends on the client; Dhruv Agnihotri argues SPAs in browsers are not fully protected against key misuse, and IETF guidance recommends the Backend-for-Frontend pattern to keep tokens and keys out of the browser, with a zero-persistence approach as an alternative when server-side infrastructure is unavailable.

- DPoP binds OAuth tokens to a client-generated asymmetric key pair, preventing replay of stolen tokens without the private key.
- Google applies DPoP only to long-lived refresh tokens, avoiding per-request cryptographic overhead on short-lived access tokens.
- DPoP does not protect browser session cookies; DBSC is being developed to bind cookies to device hardware.
- DPoP is unsuitable for multi-agent delegation; Google recommends Google Cloud STS to issue short-lived federated tokens bound to each agent's own key.
- Client-side key storage is a weak point, especially in SPAs; IETF guidance favors the Backend-for-Frontend pattern.
